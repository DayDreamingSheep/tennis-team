# Tennis Team v0.2: build contract

Status: active build spec, 2026-10-15. Source of truth for everyone building v0.2. Design intent lives in `design-brief.md` (Decisions block) and the tested prototype `prototypes/app-v3.html`; this file says how the real thing is wired.

## 1. Goal

A low-tech player installs the plugin, starts Claude once, and the Tennis Team app is already open on the Welcome screen. The app is the tested v3 design, now reading and writing the player's real workspace, with real AI replies from the plugin's skills.

## 2. Repo layout (plugin root)

```text
.claude-plugin/plugin.json        version 0.2.0
hooks/hooks.json                  SessionStart (startup) → app/launch.py, async
app/
  launch.py                       decides whether to start the server + open the browser (stdlib only)
  server.py                       local app server (stdlib only), replaces skills/voice/scripts/voice_server.py
  web/index.html                  the app (from prototypes/app-v3.html), single self-contained file
skills/
  coach/ setup/ log-note/ coach-analysis/ weekly-review/      existing, updated for state.json
  strategy/                       NEW · Strategy Coach: goal + long-term roadmap
  tournament/                     NEW · Tournament Coach: calendar, guides, match cards, debriefs, reflections
  open/                           NEW · "/tennis-team:open" → start server + open the app (replaces voice/)
  setup/scripts/init_workspace.py existing, unchanged contract
```

`skills/voice/` is removed in v0.2. Its useful parts move into `app/`.

## 3. Runtime picture

```text
Browser (app/web/index.html)
   │  fetch, token in header X-Token
   ▼
app/server.py  ── 127.0.0.1:<port>, random token, one workspace
   │  non-AI endpoints: read/patch state.json, onboarding, ticks, settings, inbox
   │  AI endpoint: queue → `claude -p --plugin-dir <root>` in the workspace (file tools only)
   ▼
Workspace folder (the player's)  ← skills read/write markdown + _system/state.json
```

**One writer at a time.** The server owns a single queue. AI jobs and non-AI state patches both go through it. A patch that arrives while a job runs is applied after the job, then the app refetches state.

## 4. Plugin data directory (`${CLAUDE_PLUGIN_DATA}`)

| File | Meaning |
|---|---|
| `.onboarded` | Exists after onboarding finishes or is skipped |
| `no-autoopen` | Exists when the player turned auto-open off |
| `workspaces.json` | `{"last": "/abs/path/to/workspace", "all": [...]}` |
| `server.json` | `{"pid": 123, "port": 8787, "token": "…", "workspace": "/abs/…", "started": "ISO"}`. Used to avoid double-starting and to reopen the page |

If `CLAUDE_PLUGIN_DATA` is unset (manual runs), use `~/.tennis-team/`.

## 5. Launch logic (`app/launch.py`)

Called by the SessionStart hook with `CLAUDE_PROJECT_DIR` (the folder Claude started in). It must return in under 1 second and never print to stdout (async hook output is discarded anyway).

1. If `no-autoopen` exists → exit.
2. If `.onboarded` is missing → start server in **first-run mode** (no workspace yet) and open `/?t=<token>` → app shows Welcome.
3. Else, if `CLAUDE_PROJECT_DIR` or a direct subfolder contains `TEAM.md` → that is the workspace. If `server.json` points to a live server for the same workspace, do nothing. Otherwise start the server for it and open the page.
4. Else → exit silently.

Server is started detached (`subprocess.Popen(..., start_new_session=True, stdout/stderr → log file in plugin data)`). The browser is opened with `webbrowser.open`. `launch.py --open` (used by the `open` skill and the double-click launcher) skips steps 1–2's silence rules and always opens, starting the server if needed, using `workspaces.json.last` when there is no workspace in the cwd.

Hook file:

```json
{ "hooks": { "SessionStart": [ { "matcher": "startup", "hooks": [ { "type": "command", "command": "python3 \"${CLAUDE_PLUGIN_ROOT}/app/launch.py\"", "async": true } ] } ] } }
```

## 6. Server API (`app/server.py`)

All routes require `?t=<token>` (page load) or header `X-Token` (fetch). Bind 127.0.0.1 only. JSON in and out.

| Method + path | AI? | Does |
|---|---|---|
| `GET /` | no | Serves `web/index.html` with `window.TT_BOOT = {token, firstRun, workspace, today}` injected before the first script |
| `GET /api/state` | no | `{ready, workspace, state, conversation, settings, jobs}`. `ready` = workspace has TEAM.md; `state` = `_system/state.json` or null; `conversation` = last 200 lines of `_system/conversation.jsonl` |
| `POST /api/folder` | no | `{choice: "documents" \| "icloud" \| "here", path?}` → resolves the folder, runs `init_workspace.py`, records `workspaces.json`, returns `{workspace}` |
| `POST /api/onboarding` | queues AI | `{answers, state}`. Writes `player/onboarding.json`, writes the provisional `state.json` the page built from local rules, writes the intro as `inbox/YYYY-MM-DD-intro.md`, writes `.onboarded`, then queues the **setup job**. Returns `{job}` |
| `POST /api/state` | no | `{patch: [...]}`: a list of `{op: "set" \| "push" \| "remove", path: "a.b.0", value}` applied to state.json. Used for ticks, Looks good / Too much, add tournament form, dismissing prompts, body-flag taps, settings mirrored into state |
| `POST /api/ask` | AI | `{text, kind, fields?}`. `kind` = intent picked by the page (`log`, `lesson`, `match-prep`, `debrief`, `sideline`, `car-talk`, `brief`, `progress`, `question`, `body`, `add-tournament`, `reflection`, `free`). Appends the user line to the conversation, queues a job. Returns `{job}` |
| `GET /api/job/<id>` | — | `{id, steps:[{member, text}], done, reply, error, members:[...]}` |
| `POST /api/settings` | no | `{autoOpen: bool, voice?, lang?}`. Writes/removes `no-autoopen`, stores the rest in `_system/settings.json` |
| `GET /plan` | no | The static plan page with `_system/plan-data.js` inlined |

**Job prompt.** The server runs `claude -p --plugin-dir <root> --output-format stream-json --verbose --permission-mode acceptEdits --allowedTools "Read Write Edit Glob Grep Skill" --append-system-prompt <APP_MODE|BOOK_MODE>` in the workspace (see Two passes below). Follow-up context comes from the conversation log, not from `--resume`. The message passed on stdin is:

```text
[app] kind=<kind> mode=<adult|parent> today=<YYYY-MM-DD>
[fields] <compact JSON of structured answers, if any>
<the player's words>
```

`APP_MODE` system prompt (summary): you are answering inside the Tennis Team app; use the `coach` skill; keep the spoken reply under 120 words, warm, plain language, max 3 next steps, no tables or headings; before replying, update the workspace files AND `_system/state.json` per the state contract; end the reply with a fenced block `tt-meta` containing `{"members": [...], "next_steps": ["…"], "state_changed": true|false}`. The server strips that block from the visible reply.

**Two passes per message (added after the first real end-to-end test).** A full skills run took 2.5–3.5 minutes per message (about 60 tool steps), and the model wasn't the bottleneck. So every `/api/ask` now runs:

1. **Fast reply:** a read-only `claude -p` with only the Read tool and the `FAST_MODE` prompt. It reads `state.json` plus the last 6 conversation lines, which are passed inline as `[recent]`. It replies in about 15–25 s, with the health rules built into the prompt. This pass is not queued behind writes.
2. **Bookkeeping:** the full skills pass with `BOOK_MODE` runs on the serialized write queue, along with patches. It receives the reply as `[replied]` and makes the files and `state.json` match what the player was told. Job field `bookkeeping`: pending → running → done | error. The page shows the reply as soon as `done` is true and refetches state when bookkeeping is done.

Onboarding stays a single full pass, because the plan review needs the written plan; the huddle covers the wait.

**Step attribution.** The server maps tool calls to friendly steps and team members: a `Skill` call sets the active member (coach → head-coach, setup → team-manager, log-note → journal-keeper, coach-analysis → coach-analyst, weekly-review → progress-coordinator, strategy → strategy-coach, tournament → tournament-coach); file edits produce steps like "Writing your journal" attributed to the active member.

**Conversation log.** `_system/conversation.jsonl`: one JSON object per line `{at, role: "user"|"team", kind, text, members?, next_steps?, job?}`. The server appends the user line on `/api/ask` and the team line when the job finishes. The page renders Home from it.

## 7. `_system/state.json` (the app's model)

Same shape as the prototype's store `S`, made explicit. Dates are ISO `YYYY-MM-DD`. Everything optional except `version`, `mode`.

```json
{
  "version": 1,
  "mode": "adult",                       // "adult" | "parent"
  "player": "Sam", "parent": "", "coach": "Maria", "academy": "",
  "level": "NTRP 3.5", "age": null,
  "goal": { "dream": "", "target": "NTRP 4.0", "by": "2027-10", "measure": "", "three_month": "",
            "family": "", "player_goal": "", "why": {"quote": "", "by": "strategy-coach"} },
  "roadmap": [ { "when": "Oct – Dec", "title": "", "focus": "", "status": "now" } ],
  "block": { "id": "CYCLE-2026-10-RETURNS", "name": "", "start": "2026-10-12", "end": "2026-11-08", "goals": [ {"t": "", "ok": false} ] },
  "week_of": "2026-10-12",
  "assignments": [
    { "k": "return", "slot": "T1", "level": "top", "area": "Top priority · Returns", "title": "", "how": "", "cue": "", "target": "",
      "status": "new", "why": { "reason": "", "quote": "", "by": "progress-coordinator" } }
  ],
  "cues": [""],
  "improving": [""], "watching": [""],
  "events": [ { "d": "2026-10-17", "t": "practice", "title": "", "state": "planned", "plan": "", "note": "", "by": "", "id": "" } ],
  "tournaments": [ { "name": "", "iso": "2026-11-08", "end": "2026-11-08", "format": "", "goal": "", "deadline": null, "entered": false,
                     "result": "", "reflection": "", "reflected": false, "matches": 0, "guide": { "before": [], "game_plan": [], "match_day": [], "between_points": [], "after": [] } } ],
  "flags": [ { "part": "left knee", "level": 1, "iso": "2026-10-15", "status": "monitor", "by": "Sam", "note": "" } ],
  "next_steps": [ { "id": "", "text": "", "due": "2026-10-17", "done": false } ],
  "team": { "active": ["head-coach", "journal-keeper", "progress-coordinator", "strategy-coach"],
            "latest": { "journal-keeper": "Logged your practice · Oct 15" } },
  "load": { "weekly_hours": { "2026-10-12": 6 } },
  "prompts_dismissed": { "id": "2026-10-16T10:00" }
}
```

Rules:
- `event.t`: practice, match, lesson, fitness, tournament, review, rest, observer, logistics. `state`: planned, done, missed.
- `flag.status`: monitor, paused, resolved, history. Level 0–3 (3 = pain/limping).
- Assignment `status` uses file terms (`new`, `keep`, `progress`, `reduce`, `pause`, `replace`, `validate`). The page translates to plain language.
- Max 3 tennis assignments + 1 fitness (`k: "phy"`).
- The page may patch: `next_steps[i].done`, `prompts_dismissed`, `tournaments` (add form), `flags` (Better/Same/Worse taps), `assignments[i]` (Too much / Looks good), `events` (add or move session). Everything else is written by skills.
- Skills keep markdown files canonical for history and evidence; `state.json` is the current picture. After any change to plan, cues, patterns, flags, events or tournaments, the skill updates `state.json` and regenerates `_system/plan-data.js` (the static plan page) from it.

## 8. File ownership

| Writer | Files |
|---|---|
| Page via server (no AI) | `player/onboarding.json`, `inbox/*`, `_system/settings.json`, `_system/conversation.jsonl`, patches to `_system/state.json` (fields listed above), plugin-data flags |
| Team Manager (`setup`) | Initial workspace, `player/profile.md`, first `training/*`, refines the provisional `state.json` |
| Journal Keeper (`log-note`) | `journal/*`, decisions/actions CSV, `state.events` (done entries), `state.flags`, `state.improving/watching`, `state.next_steps` |
| Coach Analyst | `coaches/*`, `state.team.latest`, cue changes via decisions |
| Progress Coordinator | `training/weekly_assignments.md`, `state.assignments`, `state.week_of`, `state.block`, planned `state.events` for the coming week |
| Strategy Coach | `player/goals.md`, `training/roadmap.md`, `state.goal`, `state.roadmap` |
| Tournament Coach | `tournaments/*`, `state.tournaments`, tournament `state.events`, taper events |
| Head Coach | Routing, health-first replies, `state.team`, `_system/plan-data.js` regeneration |

## 9. App behaviour changes from the prototype

- **Real dates.** `TODAY` comes from `TT_BOOT.today`; no hard-coded 2026 year logic.
- **No demo data** unless `?demo=1` (keeps the prototype's demo store and dev tab for demos).
- **Onboarding.** Welcome → `POST /api/folder` → "Who is this for?" → interview with local rules and live board (unchanged) → `POST /api/onboarding` with the board's provisional state → **huddle shows the real job's steps** → when the job finishes, refetch state → plan review renders from the AI-refined state, with Why? from `assignment.why`.
- **Home.** Renders `conversation.jsonl` + state. Free text and template answers go to `POST /api/ask` with the page's intent (`kind`) and structured `fields`. Show the local instant acknowledgement ("Logging your note…") as the job's pending card, then replace it with the real reply. The page applies nothing locally that the AI will also write; it refetches state when the job finishes.
- **Settings.** Auto-open switch → `POST /api/settings`. Whisper: v0.2 shows "Coming soon" (no fake download).
- **Offline/AI failure.** If a job errors, show "Your team couldn't answer just now. Your note is saved." The note is already in the conversation log, and an inbox file is written so the next run picks it up.

## 10. Done when

1. Fresh machine path: install plugin → start Claude in any folder → app opens on Welcome → pick Documents/Tennis → interview → real setup job runs (huddle shows real steps) → plan review shows AI-written plan with Why? → Home.
2. Close everything, start Claude in the Tennis folder → app opens on Home with the conversation and plan intact.
3. Log a practice by voice or text → real reply within about 60 s; Calendar, Plan and Team update from `state.json`.
4. Add a tournament with a deadline via the form or a sentence → Tournament Coach writes guide + events; overload check uses real state.
5. "Open automatically" off → next session in the Tennis folder does not open the app; `/tennis-team:open` still does.
6. `claude plugin validate --strict .` passes.

## 11. Natural voice and conversation (added 2026-10-15)

Decision: on-device Kokoro voices are the default upgrade; a premium cloud voice is optional; all working voices are listed for the player to choose. **Defaults:** English `af_heart`, 中文 `zf_xiaoxiao`.

### Engines
| Engine | What | Setup |
|---|---|---|
| `browser` | Web Speech voices (fallback, always available) | none |
| `natural` | Kokoro v1.0 (ONNX), on-device, free, offline | Settings → "Download natural voice" (about 360 MB, one time). Needs Python 3.10+ |
| `cloud` | OpenAI `gpt-4o-mini-tts` or ElevenLabs | The player pastes an API key in Settings; it's stored only in plugin data (`voice/cloud.json`, mode 600) and never returned to the page |

`natural` uses misaki for pronunciation (espeak is broken on macOS), so only English (US and UK) and Mandarin voices are offered: 36 voices, `af_* am_* bf_* bm_* zf_* zm_*`.

### Server API additions
| Method + path | Does |
|---|---|
| `GET /api/voice` | `{engine, voice, speed, natural: {state: none\|installing\|ready\|error, progress: 0-100, message}, cloud: {provider, configured, voice}, voices: [{id, name, lang: "en-US"\|"en-GB"\|"zh", gender, engine: "natural"}], cloudVoices: {openai: [...], elevenlabs: [...]}, defaults: {en: "af_heart", zh: "zf_xiaoxiao"}}` |
| `POST /api/voice/setup` | Starts the natural-voice install in the background; poll `GET /api/voice` for progress |
| `POST /api/voice` | `{engine?, voice?, speed?, cloud?: {provider, key?, voice?}}`. Saves choices; a key is saved but never echoed |
| `POST /api/tts` | `{text, voice?, speed?}` → audio bytes (`audio/wav` natural, `audio/mpeg` cloud). 409 `{error}` when the chosen engine isn't ready; the page then falls back to browser voices. Results are cached by a hash of (engine, voice, speed, text) |

### Spoken replies
The fast pass (`FAST_MODE`) also returns `"say"` in `tt-meta`: a spoken version of the reply, written for the ear. Under 70 words, contractions, no lists or symbols, numbers as words, the player's name, ending with a short question or nudge. The job gets `say`, and the conversation line stores it. The page shows `reply` and speaks `say`, falling back to `reply`.

### Page behaviour
- **Instant acknowledgement:** when a message is sent, immediately speak one short line ("Mm, got it. Give me a second.", "Okay, let me think about that.", "Nice, thanks for telling me."). Lines are cached per voice, so playback is instant after first use.
- **Sentence streaming:** split `say` into sentences, request `/api/tts` per sentence, start playing the first as soon as it arrives, and prefetch the next.
- **Talk mode (hands-free):** a big "Talk with your coach" toggle. After the coach finishes speaking, the mic reopens. A pause of about 1.5 s after final speech auto-sends. Tapping the big button or the reply interrupts the coach immediately and starts listening. True voice barge-in is out of scope: browsers can't reliably separate the coach's audio from the player's voice.
- **Settings → Voice:** engine choice, a grouped voice list (American / British / 中文 × female / male) with ▶ preview on each, the default marked, speed, and the natural-voice download with a progress bar. The cloud section has a provider, a key field and a voice.
- **Kids:** coach tone "Encouraging" plus a slightly slower speed (0.95) are suggested when the parent flow says the player is 12 or under.
